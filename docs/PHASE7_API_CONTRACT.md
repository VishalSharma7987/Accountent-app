# Phase 7 API contract (Documents and AI) (extends docs/API_CONTRACT.md and the PHASE2-PHASE6 contracts; same conventions)

All paths are under `/clients/{client_id}` unless stated. Amounts are 2-decimal strings, dates `YYYY-MM-DD`, `X-User` on writes, `ServiceError` -> `{code, message, details}`, voucher rule errors `422 {errors:[{rule_id, message, line_no?}]}`. Findings everywhere have the shape `{rule_id, severity: error|review|warning|info, message, field_path|null, printed|null, computed|null}` (`DocFinding.as_dict`). Rule ids D-xx: `docs/PHASE7_PLAN.md`.
New error codes: `file_rejected` (422, D-01: type / size / empty), `duplicate_document` (409, D-02; `details.document_id` is the existing document), `store_unavailable` (503, `DOCUMENT_STORE_DIR` not set or not writable), `ocr_unavailable` (409; message says what to install), `llm_disabled` (409, D-51), `llm_unavailable` (409, no `OPENROUTER_API_KEY` / `LLM_MODEL`), `extraction_invalid` (422, D-04; the invalid extraction is still stored and returned in `details`), `queue_blocked` (422, D-60: blocking findings or unacknowledged warnings; `details.findings`), `queue_state` (409, item already accepted / rejected / claimed by someone else), `queue_not_accepted` (409, D-62, hook), `mapping_missing` (422), `mapping_exists` (409), `masters_not_ready` (409, Tally vouchers queued before their masters are decided), `import_exists` (409, the same XML was imported before).
**Convention (plan decision 7):** expected failures of a model call or an extraction are returned as normal JSON bodies (status 200 with `status: "blocked" | "invalid" | "error"`, or the 409 / 422 above sent as a response, not raised) so the audit rows commit; the endpoints below say which.
Files are never served by a URL: `GET .../download` streams bytes after the usual `X-User` check.

## Documents (package A) - `api/documents.py`
- `POST /documents` multipart `file`, form `doc_type`, `financial_year_id?` -> `201 {id, sha256, size_bytes, content_type, doc_type, status:"uploaded", page_count|null}` | `409 duplicate_document` | `422 file_rejected` | `503 store_unavailable`. The file type is decided from the bytes (PDF, PNG, JPEG, TIFF; XML for `tally_xml`), never from the name; the stored name is generated; the original name is kept as metadata only.
- `GET /documents?doc_type=&status=&q=` -> `[{id, doc_type, original_filename, size_bytes, status, uploaded_by, uploaded_at, linked_voucher_ids:[...]}]`; `GET /documents/{id}` adds `{sha256, page_count, status_note, texts:[{page_no, method, engine_version, mean_confidence, char_count}], extractions:[{id, version, source, status, created_at, superseded}], queue_item_id|null}`.
- `GET /documents/{id}/download` -> the file bytes (`Content-Type` from the row, `Content-Disposition: inline`, `X-Content-Type-Options: nosniff`). `GET /documents/{id}/pages/{n}/text?method=` -> `{page_no, method, text, blocks|null}`.
- `POST /documents/{id}/read-text` body `{method?: "auto"|"pdf_text"|"tesseract"|"paddleocr"}` -> `{pages:[{page_no, method, char_count, mean_confidence|null}]}`; `auto` reads a text PDF directly and uses an OCR engine only when a page has no text layer; `409 ocr_unavailable` when OCR is needed and not installed. Document status becomes `text_ready`.
- `POST /documents/{id}/links` body `{voucher_id, link_kind: "supporting"}` -> `201 {id}`; `DELETE /documents/{id}/links/{voucher_id}` -> `{"ok":true}` only while the voucher is a draft.

## Tally (package B) - `api/tally.py`
Upload the XML first with `POST /documents` (`doc_type = tally_xml`).
- `POST /tally/imports` body `{document_id}` -> `201 {import_id, company_name, report}` | `409 import_exists` | `422` (code `invalid_tally_file`, `details.rule_id` D-30 / D-35: not well-formed, DTD / entity found, not a Tally export, unknown element, bad amount or date). Parses only; writes `tally_imports` and suggestions in `tally_master_map`; creates NO ledger and NO voucher. `report = {counts:{groups, ledgers, stock_items, vouchers}, groups:[{name, parent, suggested_group_code, decision}], ledgers:[{name, parent_group, suggested_group_code, existing_ledger_id|null, decision, reason, opening_balance_reported|null}], stock_items:[{name, unit, hsn|null, existing_item_id|null, decision, reason}], vouchers:{by_type:{...}, drafted_later:int, skipped:[{type, date, number, reason_rule: "D-34"|"D-36"|"D-37", reason}]}, opening_balances_not_applied: true}` (D-31..D-37).
- `GET /tally/imports` / `GET /tally/imports/{id}` -> the stored report and status.
- `GET /tally/masters?kind=&decision=` -> `[{id, kind, source_name, source_parent, decision, reason, target_group_id|null, target_ledger_id|null, target_item_id|null}]`; `PUT /tally/masters/{id}` body `{decision: "confirmed"|"create"|"skip", target_group_id?, target_ledger_id?, target_item_id?}` -> `{"ok":true}` (a person decides; `422` when the target does not fit, e.g. a ledger mapped into a group of another nature without confirmation).
- `POST /tally/imports/{id}/confirm-exact-matches` -> `{confirmed:int}`: confirms (as the caller) every Tally ledger whose name exists in exactly the suggested group. `PUT /tally/masters/{id}` also takes `accept_nature_change` (default false); `409 mapping_nature` when a ledger is mapped into a group of another nature without it; a Tally group can only be `confirmed` (to an existing group) or `skipped`, never `create`.
- `POST /tally/imports/{id}/apply-masters` -> `{created:{groups, ledgers, stock_items}, skipped}`: creates only rows marked `create`, through the existing group / ledger / item services (audited); never touches opening balances.
- `POST /tally/imports/{id}/queue-vouchers` body `{financial_year_id?}` -> `{queued:int, drafted:int, needs_review:int, skipped:[...]}`: for each Tally voucher whose ledgers are all mapped, a DRAFT voucher through the voucher service and a queue item (`kind = tally_voucher`); otherwise a queue item without draft carrying the findings (D-32, D-35, voucher-service errors). `409 masters_not_ready` while a ledger used by a voucher has no decision.
- `POST /tally/export` body `{kind: "masters"|"vouchers"|"both", from_date?, to_date?, financial_year_id?, posted_only?: bool}` (`409 unposted_vouchers` when the range holds draft / approved vouchers and `posted_only` is false) -> `201 {export_id, document_id, master_count, voucher_count, warnings:[...]}`: posted vouchers only (D-38, D-39); the XML is stored as a document (`tally_export`) and fetched with `GET /documents/{document_id}/download`. `GET /tally/exports` lists them.

## AI switch and model-call log (package C) - `api/ai_settings.py`
- `GET /ai/settings` -> `{llm_enabled, data_class, enabled_by, enabled_at, note, model_configured: bool, key_configured: bool}` (never the key or model secrets; the model name is shown).
- `PUT /ai/settings` body `{llm_enabled, data_class: "synthetic"|"anonymised"|"real_acknowledged", note}` -> `{"ok":true}`; enabling needs a note (D-51, D-54); audit-logged (old and new).
- `GET /ai/calls?purpose=&status=&document_id=` -> `[{id, purpose, provider, model, prompt_version, status, masking_report, tokens_in, tokens_out, latency_ms, created_by, created_at}]`; `GET /ai/calls/{id}` adds `{prompt_masked, response_raw, error_message}` (D-52; the masked prompt, never the original text).

## Extraction (package D) - `api/extractions.py`
- `POST /documents/{id}/extract` body `{mode: "llm"|"manual", payload?: <Extraction>}` -> `200 {status: "ok"|"blocked"|"invalid"|"error", extraction_id|null, llm_call_id|null, findings:[...], message}`. `llm`: needs a text read; `blocked` when the switch is off (D-51), `error` for a provider failure, `invalid` when the answer is not JSON / fails the schema (D-04: an invalid extraction row is stored, no draft). `manual`: `payload` follows the schema below (the accountant types what the document says), same checks. A new extraction supersedes the previous one only if its queue item is rejected (`409 queue_state` otherwise).
- `GET /documents/{id}/extractions` -> versions; `GET /extractions/{id}` -> `{id, version, source, status, schema_version, payload, invalid_reason, llm_call_id}`.
- `POST /extractions/{id}/check` -> `{findings:[...], recomputed:{lines:[{taxable_value, rate, cgst, sgst, igst, cess}], totals:{...}}, direction, place_of_supply}` (no write; the same engine run the queue does on every edit).
- **Extraction payload** (Pydantic, `extra = forbid`): every field is `{value: string|null, page: int|null, bbox: [x0,y0,x1,y1]|null (fractions 0..1), confidence: "0.00".."1.00"|null}`. Top level: `document_kind, supplier_name, supplier_gstin, buyer_name, buyer_gstin, invoice_no, invoice_date, place_of_supply, original_invoice_no, lines:[{description, hsn_sac, quantity, unit, unit_rate, discount, taxable_value, gst_rate, cgst, sgst, igst, cess}], totals:{taxable_total, cgst_total, sgst_total, igst_total, cess_total, round_off, grand_total}, currency: "INR", notes:[string]`. Amounts are plain decimal strings as printed (Indian commas tolerated and stripped by the engine; more than 2 decimals is D-06).

## Mappings and drafts (package E) - `api/doc_mappings.py`
- `GET /mappings/parties?q=` -> `[{id, match_kind: gstin|name, match_key, party_ledger_id, party_ledger_name, use_count}]`; `PUT /mappings/parties` body `{match_kind, match_key, party_ledger_id}` -> `{id}` (upsert; names normalised by the engine; `409 mapping_exists` for a key that already points elsewhere unless `replace: true`); `DELETE /mappings/parties/{id}`.
- `GET /mappings/lines?q=`; `PUT /mappings/lines` body `{match_kind: hsn_sac|description, match_key, party_ledger_id?, ledger_id, item_id?}`; `DELETE /mappings/lines/{id}`.
- `POST /documents/{id}/build-draft` body `{extraction_id?}` -> `{queue_item_id, status, findings:[...], draft_voucher_id|null}`: runs checks (D), resolves mappings, and only when no `error` / `review` finding remains builds the draft through the voucher service in GST invoice mode (`D-25` for the service's own errors); creates the queue item (`ai_hooks.add_queue_item`) or rebuilds the open one in place (D-27). Never creates a ledger, party or item.

## Approval queue (package F) - `api/approval_queue.py`
- `GET /queue?status=&kind=&has_blocking=` -> `[{id, kind, status, document_id, document_name, summary:{party, reference_no, date, total}, blocking_count, warning_count, draft_voucher_id|null, reviewer, created_at}]`.
- `GET /queue/{id}` -> `{...row, document:{id, content_type, page_count, download_url: "/clients/{client_id}/documents/{id}/download"}, original:<Extraction payload | tally proposal>, current:<edited payload or original>, findings:[...], draft_voucher:{id, status, voucher_type, voucher_date, reference_no, narration, lines:[...]}|null, acknowledged:[...], history:[audit rows]}`. The screen shows the document image beside the draft; `field_path` of a finding points into `current`.
- `POST /queue/{id}/claim` -> `{"ok":true}` (pending -> in_review, `reviewer` = actor; `409 queue_state` if someone else holds it); `POST /queue/{id}/release`.
- `PUT /queue/{id}/fields` body `{edits:[{field_path, value}]}` (every field of the payload is editable: header fields, each line, totals; or `{payload}` for a whole replacement) -> `{findings:[...], draft_voucher_id|null, status}`: stores `edited_payload`, re-runs checks and mappings, rebuilds / deletes the draft accordingly (D-61, D-27). The original extraction is untouched.
- `POST /queue/{id}/accept` body `{acknowledge:[{rule_id, field_path}], learn: true}` -> `{"ok":true, draft_voucher_id}` | `422 queue_blocked` (blocking findings or an unacknowledged warning). Marks the item accepted, links the document to the voucher (`source`), saves party / line mappings from the final values when `learn` (D-26), audit-logged. It does NOT approve or post: the accountant then uses the ordinary voucher approve and post.
- `POST /queue/{id}/reject` body `{reason}` -> `{"ok":true}` (reason required; deletes the draft through the voucher service; item and extraction remain, D-63).
- `POST /queue/accept-clean` body `{ids:[...]}` -> `{accepted:[...], refused:[{id, reason}]}` for items with no blocking finding and no warning (bulk acceptance of Tally vouchers); every item is accepted by the same rules as above.
- Approving / posting a voucher that is still queued -> `409 queue_not_accepted` (hook in `services/vouchers.py`, backed by the database trigger).

## Narration suggestions (package F) - `api/narration.py`
- `GET /bank/lines/{line_id}/suggestion` -> `{line_id, suggestion:{id, source: "rule"|"llm", ledger_id, ledger_name, reason, confidence|null}|null, ambiguous:[{ledger_id, ledger_name, count}], status: "none"|"suggested"|"ambiguous"|"llm_blocked"}`: rule first (D-41, D-42); the LLM only when no rule exists and the client's switch is on (D-43); the reason text always says why ("Learned from 3 earlier entries with the same narration"; "Suggested by the model from the narration; check it"). Creates a `narration_suggestions` row, never a voucher.
- `POST /bank/suggestions/{id}/accept` -> `{"ok":true}`: records the decision and teaches the rule (`narration_rules` count + 1); `POST /bank/suggestions/{id}/reject` -> `{"ok":true}`. The accountant then books the entry through the existing bank flow (D-44).
- `GET /ai/narration-rules` -> `[{id, direction, narration_key, ledger_id, ledger_name, approved_count, is_active}]`; `PUT /ai/narration-rules/{id}` body `{is_active}`.

**Tally routes are mounted under `/clients/{client_id}/tally/...`** (the `/tally/...` paths above are relative to that). A queued Tally voucher's `edited_payload` (the `original` / `current` of `GET /queue/{id}`) is `{source:"tally", tally_voucher_type, voucher_type, voucher_date, number, guid, fallback_ref, narration, reference_no, party_ledger_name, total, total_display, lines:[{tally_ledger_name, ledger_id, debit, credit}]}`; its findings keep the voucher service's own rule ids (V-xx, B-xx) plus D-31, D-33, D-35.
